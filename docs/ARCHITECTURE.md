# Architecture

```
Pro modules (private)  ──┐
                         ├──> Core interface <── Free app (UI)
Language packs ──────────┘         │
                                   ├── project model, parser, writer
                                   ├── lint, fonts, scene data
                                   └── settings, snapshots, history
```

## Where things are (after the split of Core and Free)
```
reference/python/core/lexo/        package `lexo` = Core: project model, parser, writer, checks, App (app_*.py), language packs (packs/), game tools. Imports no UI, no HTTP.
reference/python/core/tests/       Core tests (353): run with `py reference/python/run_tests.py core`; Free is not on the import path
reference/python/free/lexo_free/   package `lexo_free` = Free: server.py (local HTTP JSON server), cli.py (window, command line), ui/ (the browser UI)
reference/python/free/tests/       Free tests: the HTTP API, the UI files, the command line; `py reference/python/run_tests.py free`
reference/python/free/run_lexo.py  launcher (puts core/ and free/ on the import path), Lexo.spec / build_exe.bat build the exe from both
```
Rules: Core never imports `lexo_free`; `lexo_free` imports Core as `lexo` (absolute imports). The language packs live in Core (`rust/resources/packs`): a pack is rules for the Core
checks plus the UI texts, and the server hands the UI texts out. The tests that go through the HTTP API (`reference/python/free/tests`) are the first form of the interface contract (roadmap step 5).

## Layers
- **Core**: no UI, no network server. Everything the app does is a function of Core. A single place writes `.rpy` files (as in the old tool, `fixes.py`).
- **Free**: the application. Today it talks to Core through a local JSON API; after the Rust port it will call Core directly.
- **Language packs**: `lang/<code>` with checks and spelling for a language; Core keeps neutral checks only.
- **Pro modules**: register themselves in Core through the extension points below; Core works without them.

## The interface of Core (built: roadmap step 5)
Core is used through **operations**: `entries`, `entry/save`, `overview`, `glossary/set` ... Each is a JSON call (parameters in, a dict with `"ok": true` out), declared once in
`reference/python/core/lexo/api.py` with its method, effect (read / write / external), parameters (name, type, default, required) and a one-line description.

```python
from lexo import api
api.call(app, "entries", {"status": "todo", "limit": 10})        # the same call a script, the UI or the Rust port makes
```

- **Free's server contains no operation of its own**: it turns an address and a query string or a JSON body into `api.call(...)`. Only what needs the application around Core stays in `server.py`
  (the windows, the focus between windows, the folder dialog, the keep-alive pings).
- **The contract is data**: `testdata/contract/api.json` (what each operation takes), `testdata/contract/shapes.json` (the names and types of what each answered on the fixture project) and the
  readable `docs/API.md`. All three are generated by `py reference/python/core/tests/contract_tool.py`.
- **Tests keep it honest** (`reference/python/core/tests/test_contract.py`, `reference/python/free/tests/test_contract_ui.py`): the generated files match the code; every operation answers with the recorded shape (a lost key or
  a changed type fails); every operation is run by the test or named with a reason; the UI only calls operations that exist; the server serves each read operation like a direct call.
  The interface changes on purpose, in one visible place.
- **For the Rust port**: the same table and the same shapes are what it is checked against, plus the golden data (`testdata/golden`, docs/GOLDEN.md): fixed inputs and the recorded answers, down to the bytes of the files written.

To add an operation: write it in `api.py` (with an `example` the contract test can run, or a reason in `NOT_EXERCISED`), run `py reference/python/core/tests/contract_tool.py`, commit the three generated files with it.

## Extension points for Pro
Built (see PRO-DESIGN.md): `reference/python/core/lexo/extensions.py` is the host. A Pro feature is a **JSON call** (`host.call("publish.web", "plan", {...})`) answered by the separately delivered
Pro pack (`reference/python/pro/lexo_pro`); without the pack the feature is locked and no flag in Core or Free can change that. All five gated features (`publish.web`, `mt.batch`, `fixes.safe`, `replace.regex`, `bulk.categorize`) live in the pack; what is still open is listed in PRO-DESIGN.md.
Planned names for further features: `translate_provider` (machine translation batches), `memory_provider` (fuzzy translation memory), `exporter`, `team_sync`.
The UI shows a feature when the pack offers it, otherwise a locked hint.

## Free / Pro split
- **Free**: the whole translating workflow (see FEATURES.md): editor, proofreading, validation, find & replace, spelling, history with diff, scene preview, choices and their menu, statistics, translation generator.
- **Pro** (in the pack): batch machine translation, safe bulk fixes, regex replace, group suggestions, publishing today; carrying translations over to a new game version, fuzzy translation memory, LLM style check, character profiles, release builder, teamwork planned. Status per feature in FEATURES.md.

## Licensing and basic protection
Decided and designed in PRO-DESIGN.md: the licence is a signed file (public key in the app and the pack, private key only on the server), checked offline inside the pack, refreshed online every 30 days with a grace period,
2 devices, one-off payment per major version. The premium pack is downloaded after a licence, encrypted per licence and watermarked; Pro code is never in the public packages. It cannot be made unbreakable; the aim is that
sharing is inconvenient and traceable and that buying is simpler than working around it. Not built yet (the pack has a development stub): the licence file, the server, the sidecar transport, the signatures.
